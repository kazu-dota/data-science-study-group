# 講師用進行ガイド

## このガイドの役割

講義内容を読み上げる台本ではなく、5人の参加者がコードを動かし、結果について話す時間を守るための進行メモです。参加者の経験差は、全員が別の課題を行うのではなく、同じNotebookの`演習`までを共有し、経験者だけ`変更して確認`や`自由課題（任意）`を広げることで吸収します。

## 開講前の準備

1. Windows PCで[セットアップ手順](setup-windows.md)を最初から確認する
2. `uv sync`と環境チェックを行う
3. 全Notebookの実行チェックを行う
4. 参加者へGitHubのリポジトリURLとZIPの展開先を案内する
5. M365 Copilotへ入力してよい情報の社内ルールを確認する

```powershell
uv sync
uv run python scripts/check_environment.py
uv run python scripts/validate_materials.py --execute
```

## 毎回の準備

- 該当回の`lesson.ipynb`を上から最後まで実行する
- その回で変える値を1つ決め、講師自身の結果を控える
- `演習`開始時点のNotebookを参加者が開けるか確認する
- 共有用に「面白かった結果」を書く場所を1つ用意する
- 自習していない参加者を前提に、前回の必須知識を1分で言い直す

## 1パート（90分）の進行

全5回で、各回は3つのパート（第5回だけ4つ）で構成します。1パートがおおむね90分の1コマに対応し、下の進行はそのパート1つ分の型です。1回を通しで実施する場合は、この型をパートの数だけ繰り返します。

| 時間 | 講師の動き | 参加者の動き |
|---:|---|---|
| 0～10分 | 前パートの結果を2つ拾う | 分かったことを一言共有 |
| 10～25分 | このパートの問いと図を示す | 予想を言葉にする |
| 25～45分 | 途中で止まりながら実演 | 出力を予想する |
| 45～75分 | `演習`を巡回支援 | 全員がコードを動かす |
| 75～85分 | 5人の結果を並べる | 違いを説明する |
| 85～90分 | 1行まとめと次パート予告 | 任意課題を選ぶ |

## Notebookの使い分け

各Notebookでは、まず「基本」と「演習」を扱います。「補足」は参加者の理解に必要な場合だけ読み、
「発展（任意）」と「追加演習（任意）」は自習へ回します。各コードセルは
「これから何をするか → コード → 出力の読み方」の順です。各パートの発展内容は
[全5回の進め方の一覧](course-plan.md#発展内容の一覧)にまとめています。

- 初学者が多い回：`基本`と`演習`、必要なら`補足`まで。`発展（任意）`は結果だけ見せる
- 経験者が多い回：実演を短くし、`発展（任意）`のセルを5人で分担して読む
- 経験差が大きい回：全員が同じ`演習`まで進んだ後、初学者は`補足`、経験者は`発展（任意）`へ分かれる
- 時間が足りない回：`発展（任意）`は講師が結果だけ見せ、コード実行を`自習`へ回す

`発展（任意）`の一部（第4回パート1のXGBoost、第4回パート3のOptuna）は任意ライブラリを使いますが、未導入でも
scikit-learnの代替で最後まで実行できます。使う場合のみ開講前に `uv sync --extra advanced` を実行します。
処理が重いセル（ネストCV、反復交差検証、`RandomizedSearchCV`など）は、同期回では講師PCの結果を見せ、
各自の実行は自習へ回すと時間内に収まります。

発展内容を共有する場合は、次の4行だけを全員共通の型にします。

```text
予想：
変えたもの：
結果：
今の解釈：
```

「今の解釈」には断定でなく、追加で確認したいことを書いても構いません。

## つまずいたときの優先順位

1. Notebookのカーネルが`.venv\Scripts\python.exe`か
2. エラーが出たセルより前を順番に実行したか
3. 教材原本ではなく`workspace`へコピーしたか
4. エラー全文を読める状態か
5. 5分で直らなければ講師PCの画面で本題を継続できるか

環境トラブルを全員で待たず、本人と講師が後で直せるよう画面を残します。

## 各回の講師メモ

各回は3つのパート（第5回だけ4つ）で構成します。以下はパートごとの講師メモです。旧15回教材の各回が、そのまま各回のパートに対応します。

### 第1回：Pythonとデータに触れ、まず予測を動かす

#### パート1：予測モデルを動かす

- 到達目標：`fit`と`predict`を説明できなくても、入力と出力を指させる
- 確認する出力：1試料の活性確率が表示されるセル
- よくある誤解：確率が高ければ真実になる、学習データが多ければ必ず正しい
- 経験者：`max_depth`だけを変え、検証結果を比較する
- 注意：パート1の基本は欠損補完を分割前に行う簡略版です。正しい順序（分割→補完）と、その理由は第2回パート3・第3回パート3で扱うため、ここでは深追いしません。突っ込まれたら「第2回で正す」とだけ伝えます。

#### パート2：PythonとCopilot

- 到達目標：分からないコードを小さく切り、型と中身を確認する
- 確認する出力：エラー名とメッセージを省略せず表示する
- よくある誤解：Copilotのコードは実行できれば正しい
- 経験者：関数の入力チェックまたは型ヒントを追加する

#### パート3：pandas

- 到達目標：`head`、`shape`、`dtypes`、欠損数を自力で確認する
- 確認する出力：5人が異なるカテゴリで集計し、順位が変わる
- よくある誤解：行番号と`sample_id`は同じもの
- 経験者：複数条件、`groupby`、`agg`を組み合わせる

### 第2回：データを見て、問いを立て、評価を正しく設計する

#### パート1：EDA

- 到達目標：グラフから断定ではなく仮説を1つ作る
- 確認する出力：温度180℃、反応時間72時間の行を見つける
- よくある誤解：外れ値は自動的に削除する
- 経験者：バッチまたは系列で色分けし、見え方を比べる

#### パート2：問題設定

- 到達目標：「誰が・いつ・何を予測し・どう使うか」を1文にする
- 確認する出力：`post_assay_signal`が高性能でも利用不可と判断する
- よくある誤解：目的変数と説明変数をモデルが自動で決める
- 経験者：現在の業務判断をDummyモデルとして定義する

#### パート3：検証とリーク

- 到達目標：学習用・検証用・テスト用の役割を区別する
- 確認する出力：リーク列でスコアが不自然に上がる
- よくある誤解：高い検証スコアは必ず良い知らせ
- 経験者：`scaffold_group`単位の分割をランダム分割と比べる

### 第3回：回帰・分類・前処理Pipelineでモデルを作る

#### パート1：回帰

- 到達目標：Dummyより良いか、誤差の単位は何かを説明する
- 確認する出力：最も大きく外した8試料
- よくある誤解：R²だけでモデルの価値が決まる
- 経験者：残差を触媒や系列で分ける

#### パート2：分類

- 到達目標：偽陽性と偽陰性を利用場面に結びつける
- 確認する出力：閾値0.3、0.5、0.7でprecisionとrecallが動く
- よくある誤解：閾値0.5は常に最適
- 経験者：目的に合わせた閾値を提案し、理由を書く

#### パート3：Pipeline

- 到達目標：前処理もモデルの一部として一緒に学習する理由を知る
- 確認する出力：未知の溶媒名でもエラーにならない
- よくある誤解：欠損補完を全データで先に行ってよい
- 経験者：自作変換器（`BaseEstimator`）を書き、前処理の設定を`GridSearchCV`で選ぶ

### 第4回：モデルを比較し、特徴量と実験で改善する

#### パート1：モデル比較

- 到達目標：同じ分割・指標で比べ、用途別に候補を選ぶ
- 確認する出力：5人が1モデルずつ担当して比較表を完成させる
- よくある誤解：最も複雑なモデルが常に勝つ
- 経験者：実行時間と学習・検証差も記録する

#### パート2：特徴量

- 到達目標：化学的仮説を、予測時点で計算可能な式へ変える
- 確認する出力：特徴量追加前後を同じ分割で比較する
- よくある誤解：特徴量は多いほどよい
- 経験者：RDKitを有効にし、1記述子を再計算する

#### パート3：改善実験

- 到達目標：変更点を1つに限定し、平均とばらつきを記録する
- 確認する出力：`max_depth`だけの実験ログ
- よくある誤解：一度だけ高いスコアが出れば改善
- 経験者：重要度から反証可能な次の仮説を作る

### 第5回：提出から運用・監視・再学習（MLOps）へ

#### パート1：最初の提出

- 到達目標：問題・指標・train/test・提出形式を確認してCSVを作る
- 確認する出力：3つの`assert`を通して提出形式を検査する
- よくある誤解：提出先が正しい形式へ直してくれる
- 経験者：ベースラインを壊さず別モデルを試す

#### パート2：改善会

- 到達目標：5人の変更を実験ログへ残し、良い案だけ統合する
- 確認する出力：ローカルF1と模擬Leaderboard F1が一致しない場合
- よくある誤解：Leaderboardだけを見て変更を選ぶ
- 経験者：誤分類を系列別に調べる

#### パート3：結果共有

- 到達目標：成果の完成度ではなく、次に試す小さな問いを持ち帰る
- 確認する出力：失敗から得た学びも同じ重さで共有する
- よくある誤解：自社データをその場でCopilotへ貼ってよい
- 経験者：分割単位、ベースライン、利用者まで1枚シートに書く

#### パート4：MLOps（運用・監視・再学習）

- 到達目標：モデルを「作って終わり」にせず、学習→提供→監視→再学習のループを一続きの図で説明できる
- 確認する出力：保存したPipelineを`predict_activity()`で読み直し、新しい入力に予測を返すセル
- よくある誤解：一度良いスコアが出れば、モデルはずっと同じ性能を保つ
- 監視の観点：入力分布のずれ（敵対的検証のAUC）、予測される陽性率の変化、適用範囲（applicability domain）から外れた入力
- 再学習の引き金：監視指標が閾値を超えたとき、または新しいバッチが一定量たまったとき
- 経験者：再現性チェックリスト（乱数シード、データ版、前処理、モデル、評価条件）を1枚に埋める

## 研修後に残すもの

- 参加者が変更したNotebook
- 5人分の実験ログ
- 良かったCopilotプロンプト
- 自社テーマ1枚シート（機密情報を除く）
- 次回実施時に変えたい点を3つ以内
